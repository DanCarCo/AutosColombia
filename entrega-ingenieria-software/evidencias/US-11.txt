CASO US-11 - Rol inválido enviado por API
Fecha de ejecución: 15/11/2026
Entorno: API http://127.0.0.1:8000 · Frontend http://127.0.0.1:4200 · PostgreSQL 16 aislado (Docker, base de pruebas)
Credenciales y tokens ocultos en esta evidencia.

REGISTRO:
POST /operadores cuerpo={"nombre": "Nueva Persona", "telefono": "3000000003", "usuario": "rol_invalido", "password": "<redactado>", "turno": "DIA", "rol": "SUPERADMIN"} -> HTTP 422 {"detail": [{"type": "extra_forbidden", "loc": ["body", "rol"], "msg": "Extra inputs are not permitted", "input": "SUPERADMIN"}]}   # rol fuera de ADMINISTRADOR/OPERADOR
POST /operadores cuerpo={"nombre": "Nueva Persona", "telefono": "3000000003", "usuario": "rol_valido", "password": "<redactado>", "turno": "DIA", "rol": "ADMINISTRADOR"} -> HTTP 422 {"detail": [{"type": "extra_forbidden", "loc": ["body", "rol"], "msg": "Extra inputs are not permitted", "input": "ADMINISTRADOR"}]}   # rol válido del plan
BD: operadores antes=2, después=2

ESTADO: Aprobado
RESULTADO: API 422 y no se crea la cuenta. Observación: el rechazo se debe a que el contrato no tiene campo «rol» (extra=forbid); tampoco se acepta ADMINISTRADOR u OPERADOR, porque el sistema no implementa roles (ver INC-01).
